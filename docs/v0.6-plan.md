## 1. Export and import a single site

**Problem.** Import/export is all-or-nothing in Settings. Moving one site to the work PC, or sharing one with a colleague, means taking everything.

**Decision.**
- **Export:** an **Export** button next to **Edit** on a site's page. It downloads `NetJoin-site-<site name>-<date>.json` with that site's areas and networks.
- **Import:** **+ Add site** becomes a split button: `+ Add site ▾` → *New site…* · *Import site(s) from file…*.
- **Name clashes on import:** if a site with the same name already exists, ask: **Replace** it / **Keep both** (imported one becomes "Name (2)") / **Cancel**. That avoids the duplicate-site pile-up seen in testing.
- Export all / Import all stays in Settings (useful for moving everything to the work PC).
- File format moves to `format: 2` (adds the new fields from 5 and 6). Format 1 files still import.

❓ **Include scan results in a site export?** Proposed: optional tick box "Include device lists" (off by default), so a site file can double as a record of what was found.
❓ **Include IP history?** Proposed: no – it's personal to each laptop.

## 2. Entering the network: "IP + mask"

**Problem.** "Subnet `10.110.102.0/24`" assumes engineers know network addresses and CIDR. Many think in netmasks (`255.255.255.0`), and often only know a controller's IP from the drawings.

**Decision.** Replace the single Subnet box with two fields and a live preview:

```
IP on this network   [10.110.102.35        ]   ← any address: a controller, the laptop's IP, or the network address
Mask                 [255.255.255.0  (/24) ▾]
                     → Network 10.110.102.0/24 · usable .1 – .254 (254 addresses)
```

- The **mask drop-down** lists both forms, most common first, then the rest in order:
  `255.255.255.0 (/24) – 254 addresses`, `255.255.0.0 (/16)`, `255.255.252.0 (/22)`, `255.255.254.0 (/23)`, `255.255.255.128 (/25)` … down to `/30` and up to `/8`.
- **Pasting `10.110.102.0/24`** or `10.110.102.0 255.255.255.0` into the IP box fills in the mask automatically.
- What's stored doesn't change (`10.110.102.0/24`). Only the way it's entered and shown does.
- The network page shows the subnet the same way: `10.110.102.0 · 255.255.255.0 (/24)`.

❓ You suggested a choice between "subnet (network + CIDR)" and "range + mask". The design above covers both in one form: type *any* IP plus a mask, and the laptop range is filled in for you (item 3). Is one form OK, or do you still want two explicit modes?

## 3. Allowed range: auto-fill and shorthand

**Problem.** The "from" / "to" boxes showed `auto (.200)` / `auto (.254)`, which doesn't say what goes in them.

**Decision.**
- **Label:** "Addresses NetJoin may give this laptop", with the hint "Pick a block the site doesn't use".
- **Auto-fill** as soon as the network is known: `.200 – .254` on a /24, otherwise the top 55 usable addresses. The boxes show full addresses (`10.110.102.200`) and stay editable.
- **Shorthand:** typing `35` or `.35` expands to `10.110.102.35`. On bigger networks, `3.35` expands to `192.168.3.35` (/22 example).
- **Live check:** "11 addresses" or "outside the network" shown under the boxes.

---

## 4. "Suggest gateway"

**Problem.** "Suggest .1" is wrong on larger networks: on `192.168.0.0/22` the usual gateway is `192.168.0.1`, and on a /16 it's `x.y.0.1`.

**Decision.** Rename it to **Suggest gateway**. It fills in the network's first usable address (network + 1), and the tooltip shows the value it will use ("Use 192.168.0.1"). The **Use gateway** button next to DNS stays.

❓ Some sites put the gateway on the *last* address (`.254`). Add a second small button for that, or keep it to one?

---

## 5. Address mode: allowed range or fixed IP

**Problem.** Some sites give each engineer a specific IP. There's no way to say "always use this address".

**Decision.** In the network editor:

```
Laptop address   (•) From the allowed range   [ First free ▾ ]   from [ .200 ] to [ .254 ]
                 ( ) Fixed IP                 [ 10.110.102.39 ]
```

- **Fixed IP:** Join uses exactly that address. If another device answers for it (clash), Join **stops** and restores the previous settings, with the message "10.110.102.39 is in use by another device – check with site IT". It doesn't silently pick another address, because the site assigned that one.
- The fixed IP must be inside the network; checked on save.
- Clicking an address in IP history still joins with exactly that address, in either mode.

## 6. Allocation order (and the .200 → .35 problem)

**Problem.** After changing the range to `.35 – .254`, Join kept giving `.200`. That's the current rule: reuse the last address that worked if it's still in the range. You expected the first in the range.

**Decision.** A drop-down next to the range (see 5):

| Option | What Join tries |
|--------|-----------------|
| **First free** *(default)* | `.35`, `.36`, … upwards, skipping clashes |
| **Last free** | `.254`, `.253`, … downwards |
| **Random** | random order within the range (useful when several engineers share a range) |
| **Last used, then first** | the previous behaviour: the last working address if still in range, else first free |

- Existing networks become **First free** on upgrade (behaviour change, as requested).
- The "Next IP on Join" tile shows the method: "10.110.102.35 · first free".

## 7. Discover: quiet BACnet-only network not found

**Seen.** Laptop on **Ethernet**, joined to L2 › FCU (`10.110.102.0/24`, laptop `.39`), cable with only Siemens DXR2 controllers. Wi-Fi was connected at the same time (`192.168.3.95`). Discover found **nothing**. A normal BACnet scan on the same network, moments earlier, found all 6 controllers. _(The Wi-Fi Discover screenshot was taken later, on a different network – see item 8.)_

**Likely causes** (to confirm on the work PC):
1. **Who-Is went out of the Wi-Fi adapter.** Discover only sends Who-Is to `255.255.255.255`. With Wi-Fi and Ethernet both connected, Windows can send that out of Wi-Fi even though NetJoin chose Ethernet, so the DXR2s never received it. The BACnet *scan* also sends to `10.110.102.255`, which Windows must route out of Ethernet – which is why it worked. **Most likely cause.**
2. **Quiet network.** DXR2 controllers on their own produce very little broadcast or ARP chatter, so 20 s of listening heard nothing either.

**Quick test to confirm:** run Discover again on that cable with Wi-Fi switched off. If it finds the controllers, cause 1 is confirmed.

**Decision.**
- **Adapter picker inside the Discover dialog**, defaulting to the wired adapter. A warning appears if Wi-Fi is chosen: "Discover usually needs the BMS cable – you've picked Wi-Fi". (Not the cause here, but it makes the choice visible.)
- **With Npcap:** send the Who-Is as a raw frame **on the chosen adapter** (Ethernet broadcast), so Windows routing can't send it out of the wrong one. Npcap also hears every reply on that cable.
- **Without Npcap:** send Who-Is to `255.255.255.255` **and** to the adapter's own network broadcast address (as the scan does).
- **When the adapter is already on a network:** also run a quick ARP sweep of that network as part of Discover (only up to /22 sizes), so quiet devices still show up.
- Discover results say which methods ran ("listened 20 s · Who-Is on Ethernet · ARP sweep 10.110.102.0/24").

## 8. Discover: use the adapter's own subnet

**Seen.** Laptop on `192.168.3.95/22` (DHCP). Discover reported `192.168.0.0/24 – guessed /24`. That isn't based on the gateway: no broadcasts were heard, so it fell back to its default /24 guess, ignoring the /22 the DHCP server had just handed out.

**Decision.** Evidence for a subnet's mask, strongest first:
1. **Directed broadcasts heard** (as now) → "mask from broadcasts".
2. **The adapter's own address and mask**, when the devices found sit inside it → "mask from your DHCP lease" (or "…from your adapter settings" if static). For your case: `192.168.0.0/22`.
3. Several devices spread across neighbouring /24s → suggest the smallest network that covers them all (never bigger than /16), marked "guessed – covers all devices".
4. Otherwise `/24`, marked "guessed /24" (as now).

The likely-gateway hint also uses the adapter's DHCP gateway when there is one.

## 9. Device roll-up on sites and areas

**Problem.** Devices only show on each network's page. There's no at-a-glance view of everything found on a site.

**Decision.**
- **Site and area pages** get the same Devices panel, listing every device from every network below them, with a **Network** column (e.g. "Level 2 › FCU").
- Scanning still happens per network. On a site or area page the Scan menu is replaced by a short list: "Scan a network: FCU · AHU …".
- If two saved networks share the same subnet, their devices are shown once.
- Counts in the header: "3 networks · 42 devices · 18 BACnet · last scan 09:02".

## 10. Device table: find, sort, filter, export

**Problem.** With roll-up there will be many more rows. The All / BACnet / Other chips are good but not enough.

**Decision.**
- **Search box** above the table: matches IP, MAC, vendor, name, model and BACnet instance (e.g. type `FCU/02` or `8020`).
- **Sortable columns:** click a heading to sort, click again to reverse. Default is IP order (numeric, so `.9` before `.10`).
- **Filter chips** (keep All / BACnet / Other) plus:
  - **Web UI** – has HTTP/HTTPS open (quick way to the controllers you can browse to)
  - **Missing** – known before but **not seen in the latest scan** (useful when commissioning: a controller has dropped off)
  - **New** – first seen in the latest scan
- **Vendor filter** – a drop-down of the vendors present (Siemens, Trend…). On site/area pages, also a **Network filter**.
- **Export CSV** – the rows as currently filtered, for commissioning records and spreadsheets.

❓ Any other columns you'd filter on? Ideas: BACnet instance range, "has open ports", ping time.
❓ Later idea, not in 0.6 unless you want it: choose which columns to show.

## 11. Only one "This PC" row

**Seen.** The FCU network showed "This PC" twice: `.39` (current) and `.200` (an older address).

**Decision.** Only the laptop's **current** address is shown as "This PC". When the laptop's address on that subnet changes, the old self-row is removed at the next scan.

## 12. Navigation: breadcrumbs and a collapsible sidebar

**Decision.**
- **Clickable breadcrumbs:** each part of "50 Berkeley Street › Level 2" above the name goes to that site or area's page (which, with item 9, now shows something useful).
- **Collapsible Sites sidebar:** a **☰ Sites** toggle at the left of the top bar hides or shows the tree. The choice is remembered. Collapsed, the main area uses the full width, and breadcrumbs plus the site/area pages are enough to move around.
- **Quick switch:** typing in the search box when the sidebar is hidden opens it with the results.

❓ Collapsed state: fully hidden (more room) or a thin strip with just the toggle? Proposed: fully hidden.

## 13. Network header: drop Scan, IP history as a drop-down

**Decision.**
- **Remove the Scan button** from the network header; the Scan menu in the Devices panel does the same job.
- Add **History ▾** next to Edit / Join. It opens a floating list of the IP history (Worked / Clashed, time, internet icon), and clicking an address joins with it, as now.
- **Remove the IP history side panel**, so the **Devices panel gets the full width**, which matters most with roll-up and the extra columns.

## Data changes

`nodes` table (networks):

| Column | Values | Default on upgrade |
|--------|--------|--------------------|
| `addr_mode` | `range` · `fixed` | `range` |
| `fixed_ip` | IPv4 or empty | empty |
| `alloc` | `first` · `last` · `random` · `sticky` | `first` |

`devices` gets `last_scan_id` (or similar) so **Missing** / **New** can be worked out per scan. Export file format becomes 2; format 1 still imports. The database upgrades itself on first start, and the startup backup is taken before the upgrade.
